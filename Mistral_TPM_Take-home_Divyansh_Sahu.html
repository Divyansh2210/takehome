Annotator errors, and the steps to prevent or address them

Assumptions: the annotator is of the similar demography as the prompt creator, hence annotator's choice reflects the user's choice. This is a standalone task hence the problems rising due to continuous annotation won't be applicable here.

ErrorPrevention
Annotators can consider both responses as about the same because of them addressing separate but valid intentions instead of selecting the one which they think is correct. Make it clear in the instruction doc that the annotation needs to be done as if they wrote the prompt and chose a preferred response they will expect when they provide the input.
Annotators can skip going through other nuances of the response because they find only one of the responses following the intent correctly. This might lead to signals like wrong language usage, wrong claims go unnoticed. Introduce rubrics for critical behaviors which we want to measure separately so that annotators evaluate the model responses separately for each rubric apart from the final preference ranking. Eg: Instruction following, Factuality, Collaborativity, Verbosity, etc.

1 · Pre-submission validation

For V1, I would only automate checks which are deterministic:

  • Are all required fields present: enabled functions, user prompt and expected workflow?
  • Are the enabled functions a subset of the provided function library?
  • Do the arguments passed to enabled functions follow the function definition?

These checks should happen on the annotator side and should be mandatory clearance gates before submission. This should remove a good portion of avoidable errors before they reach the reviewer. The objective here is to avoid using reviewer time on things which can already be checked deterministically.

2 · Human review

Human review should mainly focus on checks which require judgment:

  • Does the prompt meet the required complexity?
  • Is the prompt answerable using the enabled functions?
  • Are the requirements internally consistent and sufficiently specified?
  • Does the expected workflow address all user requirements?
  • Are there any steps or outputs which do not add value in fulfilling the user intent?

3 · Future extension: LLM-assisted review

As an extension, an LLM can be used to pre-check some of the semantic areas:

  • Prompt vs enabled-function answerability
  • Prompt vs workflow coverage
  • Unnecessary workflow steps
  • Complexity classification

I would initially use these as reviewer-assist signals rather than automatic rejection criteria. Once their accuracy is validated against human review, some of these checks can potentially be moved upstream as well.

4 · Feedback loop

Recurring issues found during review should be pushed upstream wherever possible:

Repeated issue → deterministic check where possible / guideline clarification where not → annotator calibration if required

The idea is to ensure that the same type of issue does not keep consuming review effort repeatedly.

1 · Framing and assumptions

I would treat this as a modified GDPVal campaign, not a replication. The principle worth preserving is that samples represent economically useful professional work rather than academic questions built for difficulty. The brief adds complex tool interaction and possible training use, both of which change the evaluation design.

Assumptions I would make explicit:

  • 1,000 means 1,000 accepted samples.
  • A sample is prompt, input files, gold deliverable, verifiers where the task has objective components, and metadata, authored as one package.
  • Coverage is broad across Finance.
  • The agent may have any tool including web, so tool design is part of task design, and any time-sensitive value is pinned to an as-of date.
  • Downstream use may be evaluation, SFT or RL and is not fixed.
  • Volume is fixed and budget is flexible. The due date is stated as desired, so I test it in Appendix B rather than assume it.
  • A small pool of senior Finance SMEs stays in-house as domain leads and final authority. Provider capacity is Topic 4; annotator recruitment is Topic 5.

1.1 · How I'd build guidelines for a domain I am not an expert in

I own the benchmark mechanics: what we measure, how it is measured, what an accepted sample is, and how the campaign runs. The lead Finance SME owns the domain truth: why a capability matters, when it appears in real work, what a correct output looks like, and where judgment allows more than one defensible answer.

So the SME is a design partner wherever professional knowledge changes the benchmark, not someone asked to build the annotation system. A non-expert writing domain requirements alone produces a document that reads well and that practitioners do not recognise as their work. This shapes how to read what follows: the taxonomy in 2.3, the classifications in 2.2 and the realism criteria in 2.5 are domain-dependent, and my first version of each is a starting point for the lead SME to correct. Section 3 is the process for that.

2.2 · Evaluation architecture

Finance work contains both deterministically scoreable outputs and outputs where professional judgment matters. Every task is tagged objective, subjective or mixed. Objective components carry atomic verifiers: DSCR and covenant calculations, attribution, reconciliations, amortisation, forecast mechanics, correcting a broken model, specified extraction and transformation. Subjective deliverables carry no authored rubric. They are graded the way GDPVal grades: blinded pairwise comparison of a model deliverable against the expert gold, judged by an occupational expert. Board decks, investment memos, management commentary and risk recommendations sit here. Mixed tasks carry both, verifiers on the objective spine and pairwise comparison on the deliverable as a whole. Most good enterprise tasks are mixed: "build a revised forecast model and present the key changes to the CFO" has verifiable workbook calculations and a presentation that only expert comparison can judge.

Two consequences worth stating rather than leaving implicit:

  • RL usability is partial by design. Pairwise comparison needs a model output and a human judge, so it cannot serve as a reward signal. Only the verifier-covered portion is RL-usable, which makes it a coverage target in its own right rather than an accident of which subdomains happen to be calculation-heavy. I would report that share at the pilot readout.
  • Grading cost moves downstream. Not authoring rubrics removes about an hour per subjective sample from the build, and GDPVal reports over an hour of expert time per pairwise comparison at grading. The cost does not disappear, it moves to whoever evaluates the set.

Quotas are set per taxonomy cell, cell being area by workflow by evaluation type, and enforced by the assignment queue rather than by post-hoc rejection or by asking authors to track the campaign's shape. One constraint at area level: a floor of 10 percent of the set for each of the six areas, so no area ends up token. That accounts for 60 percent of the volume and leaves the rest for the lead SMEs to direct toward whatever proves most valuable based on workflow wise task quality, annotator availability and creation effort. Within an area, spread across workflows is handled by the queue drawing from unfilled cells first rather than by a fixed cap.

Duplication is a separate problem from coverage and needs a separate control. Two samples are not different because the company name, the numbers or the file names changed. Each sample is canonicalised into a structural signature of workflow, reasoning pattern, tool sequence and verifier shape, then embedded and self-clustered, with cluster sizes capped. External contamination is screened against public finance benchmarks and textbook corpora. Appendix A has the implementation.

2.4 · Complex tool interaction

Complexity has two parts, and they are checked in different places. Scale is set by the assigned complexity band in 2.6, which fixes verifier count for objective and mixed tasks and input file count for subjective ones. The author knows it before starting and does not compute anything. Shape is the reconciliation requirement, checked at review: at least two input files whose contents must be combined or cross-checked to reach the deliverable, not merely opened. Two files opened is not two files reconciled.

Two rules on top: a declared tool must sit on the minimal solution path, tested by ablation, and calls added to inflate apparent complexity are grounds for rejection. Time-sensitive retrieval is pinned to an as-of date.

Verifier quality: four required properties
  1. Atomic. One verifier tests one independently meaningful condition. If it can fail for two reasons, split it: "DSCR is correct and the covenant conclusion is stated" is two verifiers.
  2. Correct. Follows from the inputs and valid Finance logic; a second SME can reproduce the expected condition independently.
  3. Coverage of the solution path. The set covers the intermediate figures a professional has to get right, not only the final one. This is a quality property of the verifier set, checked at review against the parsed set, not a complexity measure the author computes.
  4. Reward-hacking resistant. The cheapest way to pass should be doing the work.

Property 4 is tested on our side rather than the author's, deliberately. An author who has just built the gold is the worst person to judge whether their own verifier set can be gamed, and adding it to their checklist would be asking them to attack work they are invested in. So the corrupted-output suite runs as a platform check and the author sees only the outcome: a rejection reason telling them the set was passable without doing the work, and which variant passed. The variants are: correct final number from an invalid intermediate, wrong number in the expected terminology, correct narrative missing a required calculation, hard-coded values where formulas were required, and correct output built from an unauthorised source.

Authors write verifiers as plain sentences with the value and tolerance inline, for example "revised FY revenue in the Summary tab should be 48.6 ± 0.2 USD million". Our pipeline parses those into structured checks with locators and comparison types. At the verifier density these tasks require, asking authors to hand-specify sheet references and comparison logic would add hours per task and produce inconsistent output, so the structuring belongs on our side. Verifiers that cannot be pinned to a value are classified as judgment checks, and that share is tracked, since it caps how much of the set supports RL.

2.6 · Complexity bands and measured difficulty

Two different things are tracked here, and they serve different purposes. The complexity band is assigned up front, because it has to be knowable before anyone starts work. It is a specification of task shape, not a judgment:

BandObjective and mixed tasksSubjective tasks

B230 or more verifiers3 to 5 input files
B350 or more verifiersMore than 5 input files

The queue assigns a band with the cell, so an author knows before starting what shape of task they are building, and the band is what slot rates in 7.2 are priced against. Measured difficulty is mean@5, computed after acceptance. Each sample is run five times through the probe model with tools enabled and deterministic decode settings, scored against its verifier set.

The target distribution of measured difficulty depends on the model tier being trained, which is why I would not fix a cutoff now. Most of the signal for a frontier model sits where it currently fails or passes inconsistently; a smaller model learns nothing from a set it fails everywhere. I would report the measured distribution at the pilot readout and agree the target mix there.

Two uses beyond metadata. A B3 sample the model passes almost every time goes to leak review, since a solution hint or a shortcut is the usual cause, and that mismatch between assigned band and measured difficulty is the signal worth watching. Distribution is reported per area, not only campaign-wide, so one area being accidentally easy is visible. Gold quality does not move with any of this. A wrong gold is useless for SFT and harmful for RL, so the correctness, tie-out and format gates apply identically at every difficulty level.

5 · Workflow, infrastructure and review layers

5.1 · The order an author builds in

Worth stating because it is not obvious and it moves both capacity dials. The intuitive order is prompt, then files, then solve, which is what produces input files whose totals do not foot, the most common rejection reason. The guidelines instruct the reverse:

1
Decide what the deliverable concludes and write the solution path down as a list of intermediate figures.
2
Count those intermediates against the assigned band. A band mismatch surfaces here, before anything is built, which is what makes the Gate 1 commitment safe.
3
Construct the input files backwards from the path, so totals foot by construction rather than by later correction.
4
Write the prompt last, when the requirements are known and can be stated without leaking method or file locations.
5
Produce the gold by solving the task from the files alone. Anything missing means the files are wrong, not the gold.
6
Confirm the proposed verifier candidates against the step 1 list.

Steps 1–4 are Gate 1, steps 5–6 are Gate 2. Permanent rejection and rework hours are the two inputs that drive headcount in the capacity model, and this sequence is the cheapest available reduction in both.

5.3 · The review and audit layers

Two tiers sit above authoring.

TierWhoScope
Provider QCAnnotators promoted into a QC role100 percent of submissions, guideline compliance and Finance correctness
Lead SMEsSenior in-house Finance leadsA mix of sample checks on provider QC verdicts and direct QC of annotations, plus escalations, disputes and high-risk workflows

Provider ratios are the provider's problem. What we fix is the outcome and the layers, since holding a provider to an acceptance rate rather than a headcount is what makes the arrangement enforceable.

Provider QC is staffed by promotion rather than hiring, drawing on annotators whose tasking quality the lead SME has consistently seen. Production history is the entry exam, there is no separate calibration test. Sample checking a QC verdict costs 40 to 50 percent of a fresh audit, because the trail and verifier run already exist and the only question is whether the judgment was right, which is what lets two to three in-house domain leads cover the top tier instead of ten or more.

Every new reviewer ramps supervised: their first two verdicts are fully re-checked by the lead SME, extendable at the lead's discretion. At production open, provider-nominated reviewers enter through the same supervised ramp directly, since nobody has production history with us on day one, and the promotion path takes over as production generates candidates. After the ramp, reviewer verdicts get random re-review on an ongoing slice, and the overturn rate is the control metric: a reviewer whose verdicts keep getting overturned goes back to annotation. QC is paid per task, same as authoring, and the overturn rule is what keeps per-task payment from rewarding rubber stamps.

Sampling is risk-weighted rather than uniform, oversampling newly ramped reviewers, new providers and high-complexity samples. Every rate is a floor: findings that breach threshold on any source take sampling there to 100 percent until it recovers. Planted defects from the rejected-sample library are seeded into QC queues as the cheapest live check available, since they need no comparison reviewer. Reviewer selection and promotion criteria are Topic 5.

6 · Feasibility of the requested timeline

Capacity is not one of the questions asked, so this section carries only what Section 7 needs to stand on, and what the requester needs to decide on the date. The arithmetic and its assumptions are in capacity_cost_model.xlsx, every input editable; Appendix B lists what I would re-baseline from the pilot.

At 7 authoring hours per package on average, 9.2 hours all in, and 1,087 packages authored to land 1,000 accepted, the campaign is roughly 10,600 expert hours across about eight production days, since guideline development, pilots and the requester checkpoint take the first four to six working days and final acceptance takes the last two to three. One rate chain holds everywhere in this document: 70 percent of submissions pass first time, 22 percent are recovered through rework, 8 percent are rejected permanently, which is 1,087 authored for 1,000 accepted and 92 percent acceptance once rework has run. Flat, the volume is an average of 136 submissions a day and around 240 concurrent qualified Finance SMEs at peak. Direct expert cost runs $0.9M to $1.34M, or $900 to $1,340 per accepted sample.

The plan

Commit to 1,000 in-window on a ramp, not a flat rate. The binding constraint is not sourcing bodies, Finance is a domain where providers hold warm credentialed pools at this size. The constraint is QC throughput while a new pool calibrates. So production is deliberately slow in the first two to three days, roughly 60 submissions a day under a high lead SME sampling rate with direct feedback, which is what calibrates the pool. The 60 is set by lead capacity, not provider capacity: two to three leads covering 15 to 20 checks a day is a 25 to 30 percent sampling rate, and that is the most the top tier can carry in the heavy feedback phase. As annotators prove out and are promoted into provider QC, review capacity grows and throughput scales with it, days 10 to 15 run at 170 to 190 submissions a day, which offsets the slow start and closes the 1,087 total. The campaign machinery is built for exactly this: the worked-example guidelines, the two-stage gates with same-day feedback, the author self-check and the automated stack all exist so that a large pool converges on one interpretation without a lead touching every task.

The honesty mechanism

The day 9-10 status check is the honesty mechanism. By then the leads have run two to three days at a high sample rate and the one question that decides everything is measurable: is the QC pipeline growing on curve, enough promoted provider QCs to carry the back-loaded volume. If yes, continue. If not, there is no route to 1,000 in-window, and the requester gets that same day with the pre-computed fallback, about 275 accepted at held quality, rather than discovering it in delivery week. Quality is never the variable that silently absorbs the gap.

Authoring hours and first-pass acceptance are the two numbers that move everything else. The sensitivity table on the Headcount tab runs headcount from 144 to 339 SMEs as authoring hours move between 4 and 10, which is why the pilot instruments both rather than defending an estimate.

3 · Rate negotiation

Negotiation happens after Round 2 and before contract, against the cost floor from 2.1, never against other bids. Rates are negotiated per band (B1/B2/B3), and the band mix is the lever, not the blended number. The allocation principle is output to input ratio, better annotators at better rates on tougher bands. Rates are checked against the stage time cost model for realism, quality is enforced by the measurement system, not by price. Volume tiers and share rebalancing are the remaining levers, volume share across vendors is rebalanced by acceptance rate so every vendor prices knowing share is earnable. The negotiated band rates then enter the contract as fixed prices.

Scope: the end to end contractor system, recruit domain specific expert annotators, qualify them, guarantee quality, and manage teams across subdomains through contract end. The framework is domain agnostic and is instantiated per domain through a domain advisor, the machinery stays constant and only the advisor archetype and the screening instrument change with the domain.

1 · The domain advisor

The first hire in any new domain is not an annotator. It is one senior practitioner on a fractional per hour basis, 10 to 12+ years in industry for Finance, an assistant professor or active researcher for Physics, Maths or Biology, whose job is to close my knowledge gap about the industry before I hire into it:

  1. Map the subdomains, what each one does day to day, and what a real task and deliverable look like in each.
  2. The data structures and file types practitioners actually work in.
  3. Market rates by seniority, so offers and the cost floor are grounded.
  4. Then, working with me, source the first candidates, help build the assessment items, and sit the domain interviews.

Validating the validator, since I do not have the expertise to evaluate this expert directly: backchannel references over self reported credentials, cross checking their subdomain map against public structures (GICS and standard corporate finance function maps for Finance, curriculum and arXiv taxonomies for academic domains), and where budget allows, two advisors briefly in parallel so their maps can disagree. One disclosure rule: the advisor sources from their own network, which is useful and declared, and their referrals run the same funnel with no shortcuts.

2 · The skill profile: three axes

  1. Domain depth. Has actually done the work the tasks describe. The realism test from the guidelines applies to the annotator before it applies to the task: if they cannot name the meeting a deliverable would be presented in, they cannot author it.
  2. Authoring precision. Can translate expertise into a specified task, prompt, input files, gold and verifiers, under a guideline. This is a separate skill from domain depth, and it is where most expert hires fail.
  3. Coachability. Absorbs structured feedback and converges on the guideline instead of relitigating it.

The design consequence: interviews measure axis 1 but production needs all three, so the decisive funnel instrument is a paid work sample, not a conversation.

3.1 · Scaling the funnel past the lead SME

The lead SME grades the first cohort's work samples and runs the first interviews, and both roles are then handed down. Annotators qualified from early cohorts are promoted into screening and grading for subsequent cohorts, entering through the same supervised ramp, their first verdicts and interview calls fully re-checked by the lead SME before they count, with lead SME sampling continuing at a decaying rate. Without this the funnel caps at a few dozen hires, since at 15% conversion a 240 expert pool implies ~1,600 invites and ~960 interviews, which is ~480 hours of screening that no single lead SME can absorb.

Framing note · The funnel's clock

One framing note on time: this funnel is the standing machinery for building and maintaining a pool, and it runs on its own clock, not a campaign's. Per candidate the cycle is under a week, but a pool at scale qualifies in cohort waves, because early cohorts have to be promoted into screening and grading before later cohorts can run, so a large expert pool still cannot be stood up inside a 2 to 3 week delivery window. Volume inside such a window is served by an already warm pool or calibrated external providers, while this funnel runs continuously underneath, fed by the projected lapse signal in 5.4.

4 · Guaranteeing quality

The quality being guaranteed here is annotator quality. But annotator quality has no direct gauge, the only observable is the tasks they submit, so the system below is a pipeline that converts task level verdicts into per annotator signals, and per annotator signals into staffing decisions.

The measurement instruments, in order of cost
  1. Automated gate stack first. Schema, totals footing, as-of-date pinning, verifier set passing its own gold. No human touches a sample that fails these.
  2. Reviewer QC on 100% of submissions, graded against the acceptance rubric with every rejection keyed to the guideline clause violated.
  3. Lead SME sampled review on top. Selected lead SMEs, plus annotators promoted into review through the ramp, re-check a sample of submissions directly and a sample of reviewer verdicts, heavy on each annotator's and each new reviewer's first production work and decaying with track record, and always applied to samples destined for gold or calibration use. This is the layer that catches a reviewer bench drifting, not just an annotator slipping.

These are authored task packages, not labels, so agreement metrics do not transfer directly, three people never independently produce the same package and forced convergence measures nothing. Disagreement is a two branch signal: on objective components, reviewer and author disagreeing means the guideline or the files are ambiguous, so the fix is a spec patch, not a verdict vote. On subjective deliverables, disagreement can be legitimate professional judgment, and it is protected by grading justification quality rather than forcing convergence. The reviewers are themselves instrumented too, overturn rate at re-score is tracked, and repeated flips mean the rubric or the reviewer is the problem, not the annotator.
